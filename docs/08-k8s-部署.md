# 08 在 k8s 上以 0.1 core / 512MB 部署

結論先講：**記憶體綽綽有餘，CPU 是唯一的瓶頸。** 服務可以跑，但預設參數是為
正常機器調的，在 0.1 core 下必須改。

以下所有數字都是實測的，不是估算。

## 實測數字

全部在 Docker 裡以 `--cpus=<N> --memory=512m --read-only` 實測，非換算。

### 延遲：CPU 配額的影響（單一請求，無排隊）

| CPU | 冷啟動 | `list_skills` p50 | bash script p50 | Python script p50 |
|---|---|---|---|---|
| **0.1** | 46 s | 10.3 ms | 395 ms | **2,495 ms** |
| **0.25** | 14 s | 4.8 ms | 104 ms | 723 ms |
| **0.5** | **3 s** | 2.6 ms | 11.6 ms | **132 ms** |
| 1.0 | 2 s | 2.6 ms | 10.9 ms | 67 ms |

**0.25 → 0.5 是超線性的**：CPU 加一倍，Python script 快 5.5 倍、冷啟動快
4.7 倍。這是 CFS 的門檻效應——配額足夠讓直譯器啟動在少數幾個週期內完成時，
凍結次數大幅下降。0.5 之後回到線性。

### 0.1 core 的完整分位數

單 worker，concurrency 1（每個請求獨佔，反映真實的單請求延遲）：

| scenario | rps | p50 | p75 | p95 |
|---|---|---|---|---|
| `list_skills` | 22.3 | 10.3 ms | 91.3 ms | 94.4 ms |
| `list_skills(query=)` | 16.6 | 89.3 ms | 93.6 ms | 98.2 ms |
| `load_skill` | 15.4 | 92.0 ms | 94.7 ms | 102.6 ms |
| `load_skill(section=)` | 18.0 | 89.9 ms | 92.5 ms | 192.1 ms |
| bash script | 2.5 | 395.3 ms | 490.0 ms | 702.8 ms |
| Python script | 0.4 | 2,494.9 ms | 2,602.7 ms | 2,701.3 ms |

單 worker，concurrency 16（**超載狀態**，用來看飽和點）：

| scenario | rps | p50 | p75 | p95 |
|---|---|---|---|---|
| `list_skills` | 22.9 | 598.6 ms | 604.0 ms | 2,100.6 ms |
| `list_skills(query=)` | 25.0 | 516.8 ms | 598.9 ms | 2,095.2 ms |
| `load_skill` | 19.0 | 703.8 ms | 800.3 ms | 1,201.9 ms |
| `load_skill(section=)` | 23.0 | 596.8 ms | 608.1 ms | 1,301.0 ms |
| Python script（concurrency 4） | 0.4 | 10,400 ms | 11,400 ms | 12,802 ms |

**rps 在兩種並行度下幾乎一樣（約 22），但 p50 差 58 倍。** 0.1 core 的
吞吐上限就在那裡，多送請求只會變成排隊——這正是為什麼容量規劃要看
使用率而不是看 rps 上限。

記憶體：**65.5 MB**（512 MB 的 12.8%）。映像 304 MB。

## 容量規劃

以**使用率**（utilization ρ = 到達率 ÷ 服務率）決定，不是看 rps 上限。
排隊延遲在 ρ 接近 1 時會爆炸性上升，因此要求 p95 穩定時應讓 **ρ < 50%**。

### 範例：RPM 100，2 個 pod

```
100 req/min ÷ 60 = 1.67 rps
÷ 2 pods        = 每 pod 0.83 rps   （平均每 1.2 秒一個請求）
```

| CPU | Python script 服務率 | ρ @ 0.83 rps | 結果 |
|---|---|---|---|
| 0.1 | 0.40 rps | **207%** | **崩潰**，請求無限累積 |
| 0.25 | 1.38 rps | **60%** | 危險，尖峰會排隊 |
| **0.5** | 7.6 rps | **11%** | 穩定 |
| 1.0 | 14.9 rps | 5.6% | 過剩 |

若 script 都是 bash：

| CPU | bash 服務率 | ρ @ 0.83 rps | 結果 |
|---|---|---|---|
| 0.1 | 2.5 rps | 33% | 可用，尖峰會排隊 |
| **0.25** | 9.6 rps | **8.7%** | 穩定 |
| 0.5 | 86 rps | 1% | 過剩 |

### 結論

| script 類型 | CPU request | Memory | 預期 p95 |
|---|---|---|---|
| 主要是 **Python** | **500m** | **512Mi** | script 187 ms、目錄 3 ms |
| 主要是 **bash** | **250m** | 512Mi | script 184 ms、目錄 68 ms |
| 沒有 script | 100m | 256Mi | 目錄 94 ms |

**記憶體與負載無關**：實測 65.5 MB 常駐，加上並行子行程各約 15 MB。
512Mi 是給 script 自己用的餘裕，不是服務需要。

### 2 個 pod 時，冷啟動決定滾動更新的痛感

滾動更新期間只有 1 個 pod 服務，容量減半，時間長度等於冷啟動：

| CPU | 冷啟動 | 容量減半的時間 | `initialDelaySeconds` |
|---|---|---|---|
| 0.1 | 46 s | **46 秒** | 90 |
| 0.25 | 14 s | 14 秒 | 40 |
| **0.5** | **3 s** | **3 秒** | 20 |

RPM 100 的負載下，單一 pod 撐得住短暫的雙倍流量（1.67 rps 對 0.5 core
仍只有 22% 使用率），所以 0.5 core 下滾動更新幾乎無感。

## 必改的四個參數

### 1. `--max-script-concurrency 2`（預設 8）

這是最重要的一項。0.1 core 上同時跑 8 個 subprocess，它們只是在互搶同一份
配額：總吞吐**不會增加**，但每個請求的延遲會變成 8 倍，而且更容易撞到
`stall_timeout`。

```
--max-script-concurrency 2
```

CPU 只有 0.1 core 時，能同時「真正前進」的工作本來就不到一個。

### 2. worker 數必須是 1

多 worker 是為了用滿多核心。0.1 core 連一個核心都不到，多開只會讓每個 worker
各自持有 76 MB 的索引，並且互搶配額。

```bash
uv run skill-mcp --port 8000       # 單行程，不要用 uvicorn --workers
```

### 3. probe 的 `initialDelaySeconds` 要大於冷啟動

冷啟動隨 CPU 配額差很多：0.1 core 是 **46 秒**、0.5 core 只要 **3 秒**。 加上映像拉取與節點負載波動，取實測值的兩倍再加緩衝
（`failureThreshold` 另外給幾次重試）。

設太短會讓 k8s 在服務還沒起來時就判定失敗、重啟，變成 CrashLoopBackOff——而
日誌上完全看不出錯誤，非常難查。

### 4. `--script-timeout` 要放寬

你設的 `timeout` 是 **wall time**，但在 0.1 core 上 wall time 是 CPU 時間的
10 倍。一支在開發機上跑 2 秒的 script，在這裡要 20 秒。

預設 30 秒實際只等於 3 秒的 CPU 工作。建議 **60–90 秒**。

`stall_timeout`（預設 20 秒）不用改：CFS 的凍結是 90 ms 等級，不會造成連續
20 秒沒有輸出。

## 維運端點（純 HTTP，不需要 MCP 客戶端）

| 路徑 | 用途 | 狀態碼 |
|---|---|---|
| `GET /health` | liveness：行程活著、event loop 有回應 | 恆 200 |
| `GET /ready` | readiness：**有載入 skill 才回 200**，否則 503 |
| `GET /metrics` | Prometheus 文字格式 |
| `GET /mcp` | ← **不是健康檢查**，GET 會回 405/406 |

`/ready` 在索引是空的時候回 503，因為那通常代表 `--skills` 路徑設錯或整棵樹
都被拒絕。這種狀態下接流量比不接更糟：模型拿到空目錄，然後認定這些工具不存在。

```bash
curl -s localhost:8000/ready
# {"status":"ready","skills":7,"rejected":0,"generation":1}
```

`rejected` 不為 0 代表有 skill 在磁碟上但沒被服務，可以直接拿來當告警條件。

## 建議的 manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: skill-mcp
spec:
  replicas: 2                          # 無狀態，可自由調整
  template:
    spec:
      containers:
        - name: skill-mcp
          image: your-registry/skill-mcp:latest   # 映像 304 MB
          env:
            - { name: FASTMCP_SHOW_SERVER_BANNER, value: "false" }  # 容器日誌去噪
          args:
            - --port=8000
            - --host=0.0.0.0
            - --context-tokens=30000          # 你的地端模型大小
            - --max-script-concurrency=2      # 關鍵：預設 8 太多
            - --script-timeout=90             # wall time 遠大於 CPU 時間
            - --shutdown-grace=25             # 小於 terminationGracePeriodSeconds
          securityContext:
            readOnlyRootFilesystem: true      # 服務不寫任何檔案
            runAsNonRoot: true
            runAsUser: 10001
            allowPrivilegeEscalation: false
            capabilities: { drop: ["ALL"] }
          resources:
            requests:
              # 500m：Python script 的 p50 從 2,495 ms 降到 132 ms，
              # 冷啟動從 46 秒降到 3 秒。0.25 -> 0.5 是超線性的甜蜜點。
              # script 都是 bash 的話 250m 就夠。
              cpu: 500m
              memory: 512Mi
            limits:
              # 不設 cpu limit，或設得比 request 高，讓它能 burst。
              # 設成跟 request 一樣會讓每次 script 啟動都被 CFS 切成好幾段。
              memory: 512Mi
          readinessProbe:
            # 一定要用 /ready，不能用 /mcp —— MCP 端點只收 POST，GET 會回
            # 405/406，probe 一律判定失敗，pod 會永遠 NotReady。
            httpGet: { path: /ready, port: 8000 }
            initialDelaySeconds: 20           # 500m 下實測冷啟動 3 秒
            periodSeconds: 10                 # 0.1 core 的話要改成 90
            failureThreshold: 6
          livenessProbe:
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 60           # 一定要比 readiness 更寬鬆
            periodSeconds: 30
            failureThreshold: 3
          terminationGracePeriodSeconds: 40   # 要大於 --shutdown-grace
      # 沒有 volume：服務不寫檔案，pod 掉了也沒有東西要救
```

`replicas` 可以自由調高——無狀態、無 session affinity、副本之間沒有東西要同步。

### 關於 CPU limit

**如果你能決定，不要設 `limits.cpu`。**

`requests.cpu: 100m` 保證你拿得到 0.1 core；不設 limit 則允許在節點有空閒時
burst，Python 啟動那 23 ms 就能一次跑完，而不是被切成 3 個週期。

實務上這通常是 0.1 core 環境下**最有效的單一改動**，而且不需要改任何程式。

如果政策強制要設 limit，設成 `500m` 以上，讓短暫的啟動突波有空間。

## 在這個環境下怎麼寫 script

CPU 這麼緊的時候，**直譯器啟動成本會變成主要開銷**：

| 做法 | CPU | 0.1 core wall |
|---|---|---|
| bash script（實測 p50） | — | **102 ms** |
| Python script（實測 p50） | — | **2,198 ms** |

**實測差 21 倍。** `skills/api-call/` 就是照這個原則寫的，唯讀容器內對真實 API
實測：送出型（回 uuid）**201 ms**、查詢型（回資料）**194 ms**、連不到
**199 ms** 快速失敗。直接拿去改成你的端點：

```bash
#!/bin/bash
set -euo pipefail
echo "POST $API_URL" >&2                    # 進度走 stderr
curl -s --max-time 10 --connect-timeout 5 \
     -X POST -H 'Content-Type: application/json' \
     -d "$1" "$API_URL"                     # 回應直接就是 stdout
```

需要解析、轉換、過濾時 Python 還是划算——但如果 script 只是轉發，用 bash。

另外兩個省 CPU 的做法：

- **合併 script**：與其分成 `submit.py`、`status.py`、`fetch.py` 三支，不如做
  成一支帶子命令的。每少一次呼叫就省 230 ms。
- **裝 uvloop**（`uv sync --extra speed`）：省下的是服務本身的 CPU，在配額吃緊
  時收益被放大。

## 預期表現

單一 pod、0.1 core：

| 操作 | 實測 |
|---|---|
| `list_skills` / `load_skill` | **88–92 ms** |
| 跑一支 bash script | **102 ms** |
| 跑一支 Python script | **2,198 ms** |
| 有 hooks 的 Python script | 推估 **6 秒以上**（3 個 Python 行程） |
| 4 個並行 bash（concurrency=2） | 總 644 ms，各自 419–515 ms |

**在 0.1 core 上幾乎不該用 Python script**，除非那支 script 真的需要做資料處理。
hooks 更要避免——一次呼叫變三個 Python 行程。

**在 0.1 core 上要特別節制使用 hooks**，因為它把一次呼叫變成三個行程。全域
hook 尤其要避免——那會讓每一次 script 執行都付這個代價。

## Skill 的存放與規模

### 規模對成本的影響（實測）

| skill 數 | 冷索引 CPU | refresh（無變動） | 查詢 | RSS 增量 |
|---|---|---|---|---|
| 100 | 10 ms | 0.3 ms | 0.15 ms | 1.8 MB |
| 500 | 49 ms | 1.4 ms | 0.79 ms | 6.3 MB |
| 2,000 | 201 ms | 7.0 ms | 3.7 ms | 24.4 MB |
| 5,000 | 541 ms | 20.0 ms | 14.0 ms | 63.1 MB |

線性擴展，每個 skill 約 0.10 ms 索引成本。**磁碟與記憶體都不是瓶頸**，
即使 5,000 個也只多用 63 MB。

### 兩個會被規模放大的東西

**1. 冷啟動會拖長 probe 的等待**

0.1 core 下實測倍率約 127×（42 秒 ÷ 0.33 秒 CPU）：

| skill 數 | 推估冷啟動 | `initialDelaySeconds` 建議 |
|---|---|---|
| < 500 | ~48 秒 | 90 |
| 2,000 | ~67 秒 | 120 |
| 5,000 | ~111 秒 | 180 |

> 這欄是推估，不是實測。實際部署後量一次 `/ready` 首次回 200 的時間，
> 依 RFC-155 更新這個數字。

**2. 背景 refresh 會吃 CPU 配額**

每 `--refresh-interval` 秒跑一次。0.1 core 下：

| skill 數 | 每次 wall time | 佔 5 秒週期的配額 |
|---|---|---|
| 500 | ~14 ms | 2.8% |
| 2,000 | ~70 ms | **13.9%** |
| 5,000 | ~200 ms | **40%** |

（已優化過：目錄結構沒變時不重走目錄樹，2,000 個從 25% 降到 13.9%。
剩下的是 stat 每個 `SKILL.md` 的必要成本，因為目錄 mtime 抓不到內容變動。）

### 背景掃描預設就是關閉的

**skill 在 image 裡的話，pod 生命週期內它們根本不會變**，週期性掃描是燒
CPU 去發現「什麼都沒變」，因此 `--refresh-interval` 預設為 `0`。

上面那張表是「如果開啟」的成本，說明為什麼預設要關。

只有 skill 來自**外部掛載或同步**時才需要開，這時建議 30–60 秒：

```yaml
args:
  - --refresh-interval=60    # 只在 skill 來自外部掛載時才需要
```

### 怎麼把 skill 送進 pod

本專案的 skill 平均 6.8 KB（含 scripts 與 references）。

| 方式 | 容量上限 | 改一個 description 的代價 | 適用 |
|---|---|---|---|
| **打包在 image**（目前） | 無 | build + push + 部署 + 冷啟動 | skill 變動慢、與程式碼同版本管理 |
| ConfigMap | **約 112 個** | `kubectl apply` + kubelet 同步（~60 秒） | 少量 skill |
| initContainer 拉 git → emptyDir | 無 | 重啟 pod | skill 獨立於程式碼版本 |
| sidecar 持續同步 → emptyDir | 無 | 幾秒 | skill 變動頻繁 |

**ConfigMap 有兩個硬傷**：1 MiB 是 etcd 的硬限制（base64 後實際約 112 個
skill），而且**不支援子目錄**——`scripts/` 與 `references/` 必須用 key 名
編碼，維護성很差。除非你的 skill 只有 `SKILL.md`，否則不建議。

**emptyDir 不違反 RFC-041**：那條規範說的是**服務**不寫檔案，主容器仍可
維持 `readOnlyRootFilesystem: true`；skill 目錄是另外掛載的唯讀來源。

在 0.1 core 的環境下，sidecar 會跟主容器搶同一份 CPU 配額，**除非 skill
真的變動頻繁，否則打包在 image 裡最省**。

## 什麼時候該要更多資源

如果符合以下任一項，0.1 core 就不夠了：

- `run_skill_script` 的呼叫頻率超過每分鐘幾次
- 需要用 hooks 做強制檢查
- script 本身有實際運算（不只是轉發 API）
- 需要同時服務多個使用者

那時第一個該加的是 **CPU（0.5 core）**，不是記憶體——512 MB 在上面的量測裡
連一半都用不到。

## 無狀態：不寫任何檔案

服務預設**不寫任何檔案**，可以直接跑在 `readOnlyRootFilesystem: true` 上。實測
（唯讀 + 0.1 core + 512MB）七個範例 skill 全部正常執行。

可寫目錄這個功能**已完全移除**——不是預設關閉，是不存在。有一條測試檢查
`SKILL_STATE_DIR` / `state_root` 這些名字不會在程式碼裡復活。

這代表：

- **不需要 PVC**，不需要 volume
- **pod 掉了就掉了**，沒有要救的東西
- 多副本之間沒有狀態要同步，可以隨意水平擴展
- 所有狀態都在你的後端 API 與資料庫

### 滾動更新會中斷進行中的請求

這是無狀態架構下要接受的事實，實測結果：

| 設定 | 結果 |
|---|---|
| 無 `--shutdown-grace` | `docker stop` 4 秒，請求立即中斷 |
| `--shutdown-grace=20` | `docker stop` 20.5 秒，客戶端仍 `ReadError` |
| grace=25、script 只需 8 秒 | 客戶端**仍在 6.1 秒斷線** |

uvicorn 的 `timeout_graceful_shutdown` 會延長行程壽命，但 streamable-http 的
連線在關機開始時就斷了。

**在 fire-and-forget 架構下這通常不要緊**：script 已經把工作送到你的 API，
工作照樣跑完、結果照樣進資料庫。斷掉的只是「這次呼叫的回應」。

要讓它完全不痛，需要的是**你的 API 端有冪等性**：

- 送出請求帶一個由呼叫端產生的 idempotency key
- 客戶端連線中斷後重送同一個 key，API 回同一個 uuid 而不是建立第二個任務

這比在 MCP 服務這一層做任何補償都可靠，因為只有你的 API 知道什麼算「同一個任務」。

## 驗證部署

```bash
uv run python acceptance.py --smoke     # 服務起得來嗎
uv run python acceptance.py             # 全部 75 項
```

在資源受限的環境裡跑全部驗收會慢很多（有幾項刻意測 timeout），這是正常的。
先跑 `--smoke` 確認能起來即可。
