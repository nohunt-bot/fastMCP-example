# 06 疑難排解

從症狀開始查。每一節都是實際踩過的坑。

## script 卡住 / 一直到逾時

**先看 `status`，不要先猜。**

| `status` | 意思 | 該做什麼 |
|---|---|---|
| `stalled` | 靜默超過 `stall_timeout` | **是卡住不是慢**，往下看 |
| `timeout` | 到上限時還在輸出 | 真的慢，調大 `timeout` 才對 |
| `failed` | 非零離開碼 | 看 `stderr`，這不是卡住 |

`stalled` 的結果會附上 `stdout`（死之前印了什麼）和 `silent_for_s`。如果最後
一行是 `GET /v1/orders`，端點已經告訴你了，不用再重現。

### 1. 呼叫根本沒設 timeout

最常見，佔絕大多數。`requests` **完全沒有預設 timeout**，會永遠等下去。

```python
requests.get(url, timeout=(5, 10))
urllib.request.urlopen(req, timeout=10)
```

### 2. proxy 變數沒到 script

如果 `curl` 在你的 shell 可以通、script 卻卡住，就是這個。

檢查：

```bash
uv run python acceptance.py --group 卡住偵測
```

以及 `skill_server_stats()` 回傳的 `runner.network_env_forwarded` 是否為 true。

沒有 proxy 變數時，對外連線**不會快速失敗**，而是 block 到連線逾時，所以症狀是
卡住而不是報錯。

### 3. 內網主機與 NO_PROXY

內網主機被導去外部 proxy 會在 proxy 端逾時。`NO_PROXY` 必須包含它。

注意 `NO_PROXY` 是**後綴比對，不支援 CIDR**：`NO_PROXY=10.0.0.0/8` 完全沒有作用。
要寫網域後綴，例如 `.corp.internal`。

### 4. TLS 攔截

公司的 TLS 檢查 proxy 會用私有 CA 重簽憑證，驗證會失敗，有時是慢慢失敗。把 CA
用 `REQUESTS_CA_BUNDLE` / `SSL_CERT_FILE` / `NODE_EXTRA_CA_CERTS` 傳進去。

**不要用關閉驗證來「解決」這個問題。**

### 5. 輪詢腳本被誤砍

`time.sleep()` 迴圈不印東西的話，20 秒就會被砍，就算 `timeout=300` 也一樣。

加心跳，間隔小於 `stall_timeout`。見
[03-Script-撰寫規範](03-Script-撰寫規範.md#3-長時間等待要有心跳)。

## 明明沒卡住，但回應很久

**這通常不是服務的問題，是模型 context 的問題。**

一個很普通的 500 筆內部 API 回應約 59,000 tokens。地端模型只有 30k context 時，
時間全花在 prefill 一堆它裝不下的 token 上，症狀就是「逾時」。

檢查啟動參數：

```bash
--context-tokens 30000        # 設成你的模型實際大小
```

沒設的話預設 128000，服務會放行遠超過模型能力的輸出。

驗證有沒有生效——結果裡的 `output` 欄位：

```json
{"shaped": true, "original_approx_tokens": 59222, "approx_tokens": 442}
```

更好的做法是在 script 就過濾（`--limit` / `--fields` / `--count-only`），因為服務
只能猜哪些資料重要。

## 背景任務的 uuid 不見了

任務會跑完、結果會進資料庫，斷掉的是**取回**。

### 從被砍的輸出裡撈

script 被砍時，已印出的內容仍會回傳。uuid 通常還在 `stdout` 裡，直接拿來用
`fetch`，**不要重送**（重送會產生第二個任務）。

### 從 ledger 撈

```
run_skill_script("async-job", "scripts/job.py", ["list", "--limit", "10"])
run_skill_script("async-job", "scripts/job.py", ["list", "--grep", "Q3"])
```

前提是 `--state-dir` 指向的目錄可寫。檢查：

```bash
uv run python acceptance.py --group 背景任務
```

### 預防

- script 的第一件事就是印出 uuid，再做其他事
- submit 時一定要帶 `--label`，幾週後 uuid 本身什麼都不是
- 部署時確認 `--state-dir` 可寫

---

## submit 應該很快卻很慢

`submit` 應該在幾百毫秒內回來。如果不是，**async 邊界切錯地方了**——端點在給
key 之前就先把工作做完了。

這是後端要改的，不是加 timeout 能蓋過去的。服務在 background 模式逾時的
`hint` 裡會直接這樣說。

量測方式：看結果的 `duration_ms`。

---

## 改了 skill 沒生效

1. 等 `--refresh-interval`（預設 5 秒）
2. 或呼叫 `reload_skills` 工具立即生效
3. 多工作行程部署時，各行程各自更新，會在一個週期內收斂

如果 `reload_skills` 回報 `changed: false` 而你確實改了檔案：

- 確認改的是 `--skills` 指到的目錄底下的檔案
- 確認 `SKILL.md` 存在且檔名大小寫正確
- 用 `list_skills` 確認 skill 名稱（frontmatter 的 `name` 會蓋過資料夾名稱）

## 服務起不來

先看錯誤訊息最後幾行。常見原因：

| 訊息 | 原因 |
|---|---|
| `AttributeError: 'Namespace' object has no attribute ...` | CLI 參數定義漏了（改過 `server.py` 才會發生） |
| `Address already in use` | 埠被占用，換一個 |
| `No module named 'fastmcp'` | 沒跑 `uv sync` |

冒煙測試會抓到這類問題：

```bash
uv run python acceptance.py --smoke
```

---

## skill 掃不到

```bash
uv run python acceptance.py --group 索引
```

**先看 `skill_server_stats()` 的 `index.rejected`。** 不合規的 skill 不會被載入，
但一定會出現在這個清單裡，附上原因。最常見的是 `name` 不符合 kebab-case 規則
（小寫字母、數字、連字號，最多 64 字元）。

檢查順序：

0. `index.rejected` 有沒有列出它，以及原因是什麼
1. 目錄結構是 `<skills 根目錄>/<skill 名稱>/SKILL.md`
2. `SKILL.md` 檔名大小寫正確
3. frontmatter 的 `---` 在**第一行**，前面不能有空行或 BOM
4. YAML 縮排正確（用空白，不要用 tab）
5. 名稱沒有跟其他 skill 重複（重複時會保留先掃到的，日誌會有警告）

兩種不同的失敗要分清楚：

- **YAML 語法錯** → skill 仍會載入，但當成沒有 frontmatter，用資料夾名稱當
  skill 名稱。症狀是「skill 在但 description 空白」。
- **name 或 description 不合規** → skill **不會載入**，並出現在 `index.rejected`。

---

## script 不能執行

| 訊息 | 原因 |
|---|---|
| `only files under scripts/ are runnable` | 檔案不在 `scripts/` 底下 |
| `no interpreter registered for '.xxx'` | 副檔名不在白名單。**有執行位元不算數** |
| `path escapes the skill bundle` | 路徑穿越或 symlink 指向外部 |

白名單在 `runner.py` 的 `INTERPRETERS`：`.py`、`.sh`，裝了 node 才有 `.js`。
要新增必須是刻意的決定。

---

## 吞吐量不如預期

先看 `skill_server_stats()` 的各工具 p50/p95，確認慢在哪一條路徑。

| 情況 | 處理 |
|---|---|
| `run_skill_script` 排隊 | 提高 `--max-script-concurrency`（I/O 密集調高、CPU 密集調低） |
| 有 hook 的 skill 特別慢 | 正常，hook 是 3.2 倍成本。考慮拿掉非必要的 hook |
| 整體吞吐不足 | 改多工作行程部署 |
| `list_skills` 慢 | 不太可能，這條路不碰磁碟。先確認不是客戶端的瓶頸 |

壓測：

```bash
uv run python bench.py --concurrency 16 --iterations 50
```

注意壓測程式本身是 Python，並行度拉高時會先撞到自己的上限。要可靠數字請用
非 Python 的壓測工具。

---

## 還是找不出原因

1. 開 debug 日誌：`--log-level debug`
2. 跑完整驗收：`uv run python acceptance.py`
3. 單獨執行那個 script，脫離服務：

```bash
cd skills/<skill 名稱>
SKILL_STATE_DIR=/tmp/x python3 -I scripts/<script>.py <參數>
```

第 3 步能區分「script 本身的問題」和「服務的問題」，通常一步就能定位。
