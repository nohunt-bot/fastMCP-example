# RFC-09：文件與測試

## 15. 文件 RFC

**RFC-150** 每個符合規範的服務 MUST 提供下列文件：

| 文件 | 必要 | 最低結構 |
|---|---|---|
| `README` | MUST | 見 15.1 |
| 安裝與部署 | MUST | 參數表、資源需求、健康檢查 |
| Skill 撰寫指南 | MUST | 目錄結構、manifest、檢查清單 |
| Script 撰寫規範 | MUST | 執行契約、環境變數、範本索引 |
| 疑難排解 | MUST | 症狀 → 原因 → 解法 |
| 遷移指南 | major 版時 MUST | 見 RFC-139 |
| ADR | 每個架構決策 MUST | 見 15.2 |
| FAQ | MAY | — |

### 15.1 README 最低結構

```markdown
# <名稱>
<一句話說明>

符合性等級：L1 | L2 | L3        ← MUST
規範版本：x.y.z                  ← MUST

## 快速開始                      ← MUST，可直接複製執行
## 這個服務做什麼／不做什麼        ← MUST，非目標要寫出來
## 實測數字                      ← L3 時 MUST，含量測環境
## 文件索引                      ← MUST
```

**RFC-151** README MUST 標示符合性等級與規範版本。

**RFC-152** README MUST 包含「不做什麼」小節。

**理由**：能力邊界若不明說，使用者會假設它存在。本規範中至少有三項
（不強制 `allowed-tools`、不保證關機時完成請求、不是沙箱）必須明說。

### 15.2 ADR 最低結構

```markdown
# ADR-nnn：<標題>
狀態：提議 | 採納 | 取代（被 ADR-mmm 取代）
日期：YYYY-MM-DD

## 背景            ← 問題與限制
## 決策            ← 選了什麼
## 考慮過的替代方案  ← MUST 至少一個，含未採用的理由
## 後果            ← 正面與負面都要寫
## 驗證方式        ← 如何確認決策有效
```

**RFC-153** ADR MUST 記錄至少一個未採用的替代方案及其理由。

**RFC-154** 被推翻的決策 MUST 保留原 ADR 並標記 `取代`，MUST NOT 刪除。

**理由**：本規範中多條規則的存在，是因為某個看似合理的設計被實測推翻
（例如以執行模式旗標描述輸出語意）。刪除紀錄會讓後人重蹈覆轍。

### 15.3 文件中的數字

**RFC-155** 文件中的效能數字 MUST 標註量測環境，MUST NOT 為推算值。

**RFC-156** 推算值若必須出現，MUST 明確標示為推算，且 MUST 在取得實測後
更新。

**理由**：實測顯示由完整 CPU 推算受限環境的誤差可達 14 倍。基於推算數字
設定的 k8s 探針延遲會導致 CrashLoopBackOff，而日誌上看不出原因。

## 16. 測試 RFC

### 16.1 測試類別

| 類別 | 目的 | 最低涵蓋 | 驗收條件 | 失敗即代表 |
|---|---|---|---|---|
| 單元 | 元件邏輯 | 每條 `MUST` 至少一個案例 | 全數通過 | 規範未被實作 |
| 整合 | 工具端對端 | 每個工具至少一個 | 全數通過 | 接線錯誤 |
| 安全 | 威脅緩解 | 每個威脅 T-xx 一個案例 | 全數通過 | **有實際風險** |
| 契約 | Schema 一致性 | 每個回應 schema | 全數通過 | Client 會壞 |
| 相容性 | 版本演進 | 每個 breaking 判準 | 全數通過 | 靜默破壞 |
| 迴歸 | 已修的缺陷 | **每個事故一個案例** | 全數通過 | 缺陷復發 |
| 效能 | PERF-xxx | 每條規則 | 符合門檻 | 資源超支 |
| 壓力 | 資源上限 | 並行、大輸出、大 stdin | 不崩潰 | DoS 面 |
| 冒煙 | 可啟動 | 實際啟動並回應 | `/ready` 200 | **單元測試測不到的部署錯誤** |

**RFC-160** 每一條 `MUST` 規則 MUST 有對應的自動測試。

**RFC-161** 每一個修復過的缺陷 MUST 有迴歸測試，且測試的 docstring
MUST 說明原本的失敗行為。

**理由**：「為什麼有這條測試」比「這條測試做什麼」更難重建。缺少此說明
的測試會在重構時被當作噪音刪除。

**RFC-162** 測試套件 MUST 包含**冒煙測試**：實際啟動服務並確認其回應。

**理由**：實測案例——CLI 參數定義遺漏導致服務完全無法啟動，但全部單元
測試通過，因為它們都直接呼叫內部建構函式，繞過了 CLI。

### 16.2 安全測試的特殊要求

**RFC-163** 安全測試 MUST 執行真實的攻擊，MUST NOT 只驗證防護函式的
回傳值。

| 不合規 | 合規 |
|---|---|
| 斷言 `is_safe_path("../x") == False` | 實際建立指向 `/etc/hosts` 的 symlink 並嘗試讀取 |
| 斷言封鎖清單包含 `PATH` | 實際傳入 `env={"PATH": 假目錄}` 並確認假執行檔沒被執行 |

**RFC-164** 每個安全測試 MUST 同時驗證**正常用途未被誤傷**。

**理由**：過度封鎖與封鎖不足同樣是缺陷。封鎖 `PATH` 的同時必須確認傳遞
`API_TOKEN` 仍然可行。

### 16.3 效能測試

**RFC-165** 效能測試 MUST 在目標部署的資源限制下執行。

**RFC-166** 效能測試的報告 MUST 包含量測環境描述。

**RFC-167** 效能結論 MUST NOT 由較寬鬆環境的數字推算。

### 16.4 驗收流程

**RFC-168** 專案 MUST 提供單一指令的驗收流程，其輸出 MUST：

| 要求 | 理由 |
|---|---|
| 每項只有通過／失敗兩種結果 | 執行者不需判斷力 |
| 失敗時說明「為何重要」與「下一步」 | 可由不熟悉專案者修復 |
| 可分組執行 | 一次只處理一件事 |
| 結尾為明確結論 | 不留模稜兩可狀態 |
| 離開碼有語意 | 可接入 CI |

**RFC-169** 驗收流程 MUST 可由能力較弱的自動化代理執行，其文件 MUST
包含可直接複製給代理的指示，且該指示 MUST 包含停止條件。

範例停止條件：

```
- 一次只修一項
- 不得修改測試來讓它通過
- 同一項連續失敗 3 次即停止並回報
```
